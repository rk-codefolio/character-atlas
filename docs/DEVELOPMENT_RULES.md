# 開発ルール

## 設計と依存方向

- 図鑑、投稿、モデレーションの境界とユビキタス言語を定義する。型の設計では、業務上の同一性、値としての等価性、整合性を一緒に守る範囲を確認する。
- プレゼンテーション層は REST の入出力を扱う。アプリケーション層はユースケースの流れとトランザクションを扱う。ドメイン層は業務ルールを扱う。インフラストラクチャ層は永続化・外部連携を実装する。
- 依存は内側へ向ける。レイヤーの境界で外部実装が必要な場合は、利用する側がポートを定義する。Spring や MyBatis の設定と組み立ては外側に置く。
- パッケージ名から機能とレイヤーを特定できるようにする。クラスは同じ理由で変わる処理をまとめ、責務が異なる処理を分ける。
- PostgreSQL のクエリーはインフラ層の MyBatis Mapper に置く。スキーマ変更には Flyway を使い、適用済みのマイグレーションは保持する。

## Java

- Java 25 を使用し、Java 21〜25で正式化された機能を、処理の意図を明確にできる箇所で積極的に使う。
- [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html) に準拠する。各クラス・メソッド・変数を日本語で説明し、役割、制約、判断の理由が読み取れるようにする。
- 固定された選択肢には `enum`、種類によってデータや規則が異なる閉じた型には `sealed` を使う。 `enum` と `record` は各ファイルのトップレベルに定義する。
- 値がないことが正常な戻り値は `Optional` で表現し、空の集合は空コレクションで返す。外部から受け取った `null` は境界で処理し、必須値は生成時に検証する。
- コレクションの絞り込み、変換、集計には原則 Stream API を使う。走査回数を減らすなど明確な理由で `for` を使うときは、日本語コメントで理由を書く。
- モジュールや成果物は実際の役割に合わせて命名する。名前に `demo` を使わない。

## テスト

- JUnit の各テストに「何を確認するか」「前提と操作」「期待結果」を日本語で記載する。
- 共通基盤と公開アプリの本番 Java ソースを対象に、単体・統合テストを合算した行カバレッジを 90%以上とする。基準を下回る場合は検査を失敗させる。
- API・DBを変更する場合は、既存データの移行と公開 REST API の振る舞いを確認する。

## PR 運用

- PR には目的、変更範囲、検証方法と期待結果、実行結果を記載する。
- 人間のレビュー対応と Codex のレビュー対応は別の PR で扱う。
- `main` へのマージを確認したら GitHub 側の作業ブランチを削除する。手元の作業ブランチは保持できる。

## ドメイン検証と例外

- ドメイン型は自身の不変条件を定義し、コンストラクタから共通の検証処理を呼ぶ。登録済みデータの実在確認はアプリケーション層で行う。
- エラーメッセージは機能ごとのカタログにまとめ、`TITLE_REQUIRED` のように違反内容が分かる定数名で参照する。
- アプリケーションが定義する失敗は独自例外で表し、型で想定内と想定外を判別できるようにする。共通の REST 例外ハンドラーで HTTP 応答に変換し、想定外の原因はサーバーログに残す。

## Javadoc とパッケージ

- [JDK 25 Javadoc 仕様](https://docs.oracle.com/en/java/javase/25/docs/specs/javadoc/doc-comment-spec.html) と [Oracle の執筆ガイド](https://www.oracle.com/java/technologies/javase/writing-doc-comments.html) に沿い、要約、入力の意味、生成時の保証、戻り値、副作用、例外条件を日本語で記載する。sealed 型では共通の契約と各実装型の違いを説明する。
- 機能、レイヤー、責務の順にパッケージを整理する。閉じた型の実装は親型の近くに置く。

## Mapper SQL の配置

- 単一テーブルの固定 SQL で結果マッピングが単純なものは Mapper インターフェースに置く。JOIN、CTE、サブクエリ、動的 SQL、一括処理、複雑な結果マッピングを含むものは Mapper XML に置く。
- 単一テーブルに対する固定の `SELECT EXISTS (SELECT 1 ...)` は単純な存在確認としてインターフェースに置く。
- Mapper XML は対応する Java Mapper と同じパッケージ階層に置く。移行した SQL は PostgreSQL 統合テストで引数、条件分岐、結果マッピングを確認する。
