# AIを使った開発記録

「風綴りの群島」は、技や効果でキャラクターを探す図鑑のポートフォリオです。使用したAIツールは **OpenAI Codex** です。以下では、対話で検討した選択肢、私が決めたこと、Codexが実装・検証した結果を対応づけています。別途、公開ソースを参照できる題材で同じ調査方法を確かめました。[オープンソースゲームの分析事例](WESNOTH_ANALYSIS.md)

## 作業時間

初回公開までに、人間が要件を考え、画面を確認し、公開準備を進めた時間は **約5時間**（目安は4〜6.5時間）です。対話履歴を工程別に振り返った事後見積もりです。Codexの処理を待つ時間と、公開後のコードレビューは集計対象外です。

| 工程 | 人間が行ったこと | 概算 |
| --- | --- | --- |
| 要件定義と壁打ち | 検索の対象、画面の役割、仕様の優先順位、調査で判断できる範囲を決めた | 1.5〜2.5時間 |
| 試作の確認と修正 | 一覧・検索・詳細の表示を確認し、並び順、属性の表示、検索条件について具体的に指示した | 1.5〜2.5時間 |
| 公開準備 | 共有するモジュール、起動方法、開発記録の内容を決め、GitHubで登録と表示を確認した | 1〜1.5時間 |

## 1. 課題を整理し、調査を検索仕様につなげる

- **依頼**。スキル説明、効果の定義、検索タグを照合し、同じ名称で異なる効果がある場合も扱えるようにしたい。
- **AIの作業**。表示用の説明、効果への明示参照、分類上の関連を分けた。各判断について、どの情報が確認でき、どの挙動が未確認かを整理した。
- **私の判断**。根拠が弱い候補も検索に含める。表示順とラベルで明示一致と区別し、一覧の初期順には図鑑順を使う。
- **壁打ちで詰めた点**。候補を残すと、ANDとORで何を「明示一致」とみなすかが曖昧になる。たとえば「護り」は候補で「回復」は明示されている場合、ANDでは関連候補にし、ORでは「回復」だけで明示一致にする。この具体例を、順位まで再現できる仕様にした。[検索の例](../README.md#調査を検索仕様に落とした例)
- **実装**。効果・タグへの明示参照と関連候補を別の根拠として保持。ANDでは全条件が明示された結果、ORではいずれかが明示された結果を優先し、同じグループの中は図鑑順にした。[根拠のモデル](../catalog-core/src/main/java/dev/characteratlas/domain/character/CharacterProfile.java) · [検索と並べ替え](../catalog-core/src/main/java/dev/characteratlas/application/search/CharacterCatalog.java)

## 2. 提案を画面で確かめ、要件を修正する

| やり取りの要旨 | 私の判断 | 画面への反映 |
| --- | --- | --- |
| 共有方法を検討するうちに、Codexの提案でイベント日程が独立した導線になっていた | イベントはコンテンツを整理するための資料と整理し、利用者がまず使うキャラクター検索を優先した | 公開版の主な画面を「渡り手一覧」「技で探す」「キャラ詳細」にした |
| 一覧でステータスの違いをどこまで見せるか | 一覧は見つけるために使う。比較表は設けず、選んだステータスで昇順・降順に並べる | 図鑑順を初期値にし、速度などを選んだときにその数値をカードに表示した |
| キャラクターの属性が分かるようにしたい | 一覧でも詳細でも、名前と属性をすぐ確認できる形にしたい | 属性を色・文字・記号で表示し、一覧・検索結果・詳細で同じ表記を使った |

AIには、修正後の導線と操作手順を具体化し、実際の画面を開いて確認する作業を任せました。[画面の試し方](../archipelago-app/README.md#試し方)

## 3. 実装と公開範囲を決める

- **私の判断**。独立した見本を作る案を見直し、検索ルールを持つJava・DDDの共通基盤と、架空データを使うアプリを共有する方針にした。Dockerで画面からDBまで起動できるようにし、最初のREADMEから試し方へ進めるようにした。
- **AIの作業**。ドメインモデルと検索処理を共通基盤に置き、データの読み込み先をインターフェースで分離した。公開アプリではSpring BootのAPIからPostgreSQLを読み、Next.jsで表示する。架空の6人・技・効果の関連はFlywayで初期登録した。
- **公開前の確認**。公開用に切り出したフォルダーでビルドし、Gitの登録対象を点検した。DBとAPIはCompose内で通信し、ブラウザ向けのポートだけをローカルに公開する。[共通基盤の構成](../catalog-core/README.md) · [初期データ](../archipelago-app/src/main/resources/db/migration/V100__archipelago_catalog.sql) · [Docker構成](../archipelago-app/compose.yaml)

## 4. 技術選択を問い直す

- **やり取りの要旨**。最初はJava 17を使っていた。私から最新LTSへ更新するよう依頼し、続けて「ソースの書き方も新しいJavaに合っているか」を確認した。
- **AIの作業**。ビルドとDocker実行環境をJava 25に揃えた。検索結果の比較条件を一つにまとめ、明示一致の優先と図鑑順の関係をコードに表した。DBの版番号を読む箇所では `JdbcClient`、行マッピングの未使用引数には `_` を使った。
- **判断**。技術の更新は、ビルド環境とコードの変更を分けて確認した。検索仕様を保つことを受け入れ条件にした。[Javaの設定](../catalog-core/build.gradle) · [DBの読み取り](../archipelago-app/src/main/java/dev/characteratlas/archipelago/catalog/infrastructure/persistence/snapshot/PostgresCatalog.java)

| P3 | DBに基本値と異なる覚醒後の値があっても、詳細APIの `maxAwakenedStats` に基本値が入る。[DBアダプター](../archipelago-app/src/main/java/dev/characteratlas/archipelago/catalog/infrastructure/persistence/snapshot/PostgresCatalog.java) | 覚醒後の値を詳細APIで扱うか、公開版のレスポンスから外すか判断する | PR #2で修正 |

## 公開版の機能を見直した経緯

初回公開版を確認した私は、図鑑だけでは設計・実装の範囲が伝わらないと判断しました。公開するデータや世界観を架空に差し替えつつ、検索の共通基盤、REST API、投稿・通報・管理といったアプリの機能を揃えるようCodexに依頼しました。Codexは機能とAPIを照合し、架空データの初期登録とDBを使う統合テストを追加しました。[構成図と仕様](ARCHITECTURE.md)

## Codexコードレビュー第2回

機能拡張をマージした `8b2520d` を対象に、初回公開後の差分をCodex CLIの `codex review` で確認しました。優先度はCodexが付けたものです。[レビュー対象コミット](https://github.com/rk-codefolio/character-atlas/commit/8b2520d)

| 優先度 | 指摘 | 対応 |

| P3 | Discord通知が文字数上限を超える設定を受け付ける | 起動時に実際の通知文の長さを検証し、上限を超える設定を拒否 |
